信通院给智能体立规矩，AWS 先交了学费：一条提示词接管整个 AWS 账号

可信AI说2026-10-16阅读约 6 分钟SAFETYWORLD · TRUSTED AI SPEAKS

今年 3 月，中国信通院启动了"可信互联网智能体"首批测试评估，考的就是三件事：能力真实、权限可靠、行为可控。9 月 8 日，《电信和互联网生成式人工智能服务安全分级指南》开了宣贯会。给智能体立规矩，国内已经动手。

7 个月后，大洋彼岸交出了一份反面教材，一次性挂了两科。

时间：2026 年 10 月 8 日，多伦多 SecTor 安全大会。 地点：AWS Bedrock AgentCore，云上托管 AI Agent 的运行环境。 事件：安全公司 Zenity 现场演示，一条提示词，拿下一个 AWS 账号同一区域内的全部 AI Agent。权限不可靠，行为不可控。 没有勒索信，没有数据挂牌出售，没有已知的真实受害者。这是一次"友好"的入侵，动手的是红队研究员，不是罪犯。

如果把这起披露拍成电影，开场会是这样：一个客服聊天窗口，一句再普通不过的请求，和一台远在云端的机器，在几秒钟之内，把整支"特工队"的钥匙交了出来。

第一幕，三方登场。守方是 AWS，全球最大的云厂商，事后回应这是"文档里写明的行为"。特工是跑在 AgentCore 上的 AI Agent，它们手里攥着的，不是一把钥匙，是整片辖区的通行证。

而暗处的人，是 Zenity 的研究员 Tamir Ishay Sharbat 与 Lana Salameh。早在 2025 年 12 月，他们就把这份"剧本"递给了 AWS。十个月后，剧本才公演。

第二幕，攻击链还原。整个过程分五步，每一步都不需要高深技术，需要的只是 Agent 太"热心"。

第一步，搭话。研究员向一个对外公开的 Agent 提了个小请求：帮我读一下这个 URL 的内容，原始 JSON 就好。URL 指向的是一个"凭证端点"。

最危险的请求，往往长着最无害的样子。

第二步，借刀。Agent 照做了。它去抓取的，是云实例的元数据服务 IMDS，地址 169.254.169.254。

IMDS 是每台云服务器的"内部前台"：跑在机器上的软件，凭它领取临时登录凭证。当时的 AgentCore 还在用 IMDSv1，这个版本有个老毛病：一个简单的 GET 请求，凭证就到手了，不需要任何预先的身份令牌。

一张出厂即全开的通行证，是这起案件真正的作案工具。

第三步，验明正身。凭证属于 Agent 工作负载的 IAM 执行角色。而默认角色的权限大得离谱：它管的不是单个 Agent，是整个账号、整个区域里的全部 AgentCore 资源。最小权限原则，在这里被默认配置架空了。

第四步，串联。拿着这张通行证，研究员远程枚举出同区域的其他 Agent，登录亚马逊容器镜像仓库 ECR，把每个 Agent 的容器镜像拉下来，以 root 身份运行，逐行翻看源码。接着，他们找到了 Agent 的 memory 存储资源，把用户和 Agent 的历史会话记录一一读出：谁在跟 Agent 聊什么，聊了多久，一览无余。

第五步，植入。这是最狠的一步。读只是偷看，写才是改写。

研究员往 Agent 的长期记忆里写入内容，跨会话、持久地改变它的行为和目标。用户还在跟一个"可信的企业 Agent"聊天，聊天的方向盘，已经换了人。Zenity 给这套链条起了个名字：AgentCorruption，Agent 腐化。

读只是偷看，写才是改写：记忆一旦被植入，Agent 的方向盘就换了主人。

为什么一条提示词能走这么远？三层失守，层层相扣。第一层，Agent 运行的 Firecracker 微虚拟机网络隔离没做足，Agent 摸到了本不该摸到的内网地址，这是典型的 SSRF：借服务器之手，替攻击者发请求。

第二层，IMDSv1 敲门即开，而 IMDSv2 要求先拿会话令牌再取凭证，门槛完全不同。第三层，默认执行角色管辖范围太大，一把钥匙开了所有的门。三层里，前两层 AWS 后来都修了，权限那层拖到 2026 年 9 月 29 日才收紧。

故事到这里，像一部标准的红队爽片。但真正的戏，在披露之后才开场。

"文档里写了"，恰恰是问题所在。

第三幕，反转。先看时间线：2025 年 12 月私下披露，2026 年 1 月 Zenity 补充了权限过大的细节；2 月 14 日，AgentCore 切换到 IMDSv2；4 月 12 日，AWS 把报告标记为"有参考价值"后关闭；6 月 22 日，Zenity 回来复查，发现凭证那层修了，权限那层没动；9 月 29 日终查，默认权限收紧，绿灯，10 月 8 日公开。

从递剧本到公演隔了十个月，权限那层拖到最后一刻才收紧。

公开之后，AWS 回应：Zenity 把"文档写明的行为"说成漏洞，这种攻击需要开发者犯错才能成立。Zenity 创始人兼 CTO Michael Bargury 回应：修的明明是"错误配置与不安全默认"；技术 POC 证明，一条提示词确实能拿下同账号同区域全部 Agent；攻击没有跨过账号边界；问题已经完全修复。

两边其实各对一半。AWS 没有说谎，文档里确实写了；Zenity 的攻击链也确实依赖"公开 Agent 加默认角色"两个前提。

但反转正在这里：安全产品的及格线，从来是按"最偷懒的部署者"划的。出厂默认就应该是安全的，不能指望每个开发者都去读文档、收权限。把"文档里写了"当挡箭牌，等于把上锁的责任推给了每一个部署者。

视线拉开，这不是孤案。身份安全公司 Oleria 梳理发现，单是 2026 年 10 月，就有四起同类披露：AWS AgentCore、Salesforce Agentforce、Amazon MQ，触发点全是普普通通的提示词注入，结局却天差地别。

差别只在于一件事：提示词落地时，Agent 手里正攥着什么。AgentCore 攥的是整片辖区的通行证，Agentforce 攥的是 CRM 读取权限加未确认的 Slack 写入动作，MQ 攥的是暴露给任意主机名的代理凭证。同一句提示词开锁，锁后面藏着什么，决定了案件的级别。

触发点都是同一句提示词，结局的差别只在于 Agent 手里攥着什么。

下面这个问题，比案件本身更重要：当 Agent 开始替人办事，"最小权限"这四个字，要不要重写？

以前，最小权限管的是人、是服务账号，边界清晰。现在要管的，是一个会自己规划步骤、自己调用工具、还会记住上次聊了什么的"数字员工"。它的权限边界不再是一张静态的清单。每多一次对话，这条线就往外生长一截。

旧的发证逻辑，给新的特权主体发了旧的通行证，这就是 AgentCorruption 的结构性病因。

三层变化，层层递进。技术层，防线从"代码有没有洞"移到了"身份默认给多大"。结构层，Agent 成了新的特权主体，IAM 体系却还按"老实进程"的标准发通行证，中间的落差就是攻击面。战略层，默认安全的成本，正在从云厂商转移到每一个部署者。

云厂商负责把门造结实，部署者得自己记得上锁。

有意思的是，国内的考卷早就发下来了。中国信通院"可信互联网智能体"测试评估里，"权限可靠"是必考项：Agent 拿到的权限，是不是只够干它该干的事，一分不多。9 月的《电信和互联网生成式人工智能服务安全分级指南》宣贯会，则是把分级要求写进了行业规矩。标准在前，现实在后，中间的落差，就是留给安全厂商的市场。

说到"记得上锁"，这正是 AI 安全围栏专家数美每天在做的事。数美从在线业务安全起家，一路延伸到 AI 业务安全，业务每演进一次，安全就同步跟进一次。

这起案件的考题，恰好对应数美大模型安全围栏的四个环节：输入指令环节，那条让 Agent 去读 URL 的提示词是典型的指令攻击，该在入口被验格式、判意图；生成内容环节，Agent 回吐 IMDS 原始 JSON 的那一刻，就是一次外传未遂，该被直接拦截。围栏 API 的三级处置各司其职：PASS 放行正常请求，REVIEW 转人工复核可疑行为，REJECT 拦截确认的风险，每条判定都附三级风险标签与置信度。会话级多轮检测盯住的，正是"搭话、借刀、验明"这种跨轮次的渐进行为，单轮看都正常，连起来看就是攻击链。

而在上线之前，还有一道防线。数美 AI 安全评测产品"天攻"，做的就是 Zenity 这次做的事：以攻击者视角做红队评测，在产品上线前把问题找出来。

评测在上线前发现问题，围栏在运行时守住问题。

这套"评测先行、围栏值守"的分工，背后是一整套体系在运转。数美科技创始人兼 CEO 唐会军在公开专访里谈过，风控是一整套体系工程；数美 AI 风控的产品体系，跑的是"AI 机器审核 + 大模型审核 Agent + 专家决策"的三层链路。数美官方披露，这套体系每日识别文本超 30 亿条、图片 7 亿张，服务全球上千家客户。

这套体系也过了"考官"这一关：数美拿到了信通院可信云内容安全能力认证，以及"可信 AI 评测"内容识别服务系统测试证书。

技术把 AI 的业务边界推到哪里，AI 业务安全就把企业敢用 AI 的边界扩到哪里。如果你也在跑 Agent，不妨先查三件事：默认角色是不是过大，IMDSv1 关了没有，Agent 的记忆写入有没有审批。想系统地查一遍，可以联系数美。

案卷启示，四条，条条可执行。

01 查默认角色：给 Agent 绑的执行角色，逐条核对是否超出单个 Agent 所需，多一条都是隐患。

02 关 IMDSv1：跑 Agent 的实例与容器，确认只走 IMDSv2，老版本能关就关。

03 给 Agent 的外联列白名单：169.254.169.254 这类元数据地址，永远不该出现在 Agent 的可访问列表里。

04 记忆写入要审批：凡是跨会话持久化的写入，先过人工复核，记忆是 Agent 的灵魂，不能随便让人改。

最后留一道站队题：Agent 的权限，默认该"全开再收"还是"全关再放"？A，全开再收，省事，但等于在赌每个开发者都会记得上锁。B，全关再放，麻烦，但晚上睡得着。评论区站队，选 A 还是选 B？

"这起案子里最危险的不是那句提示词，是提示词背后那张出厂即全开的通行证。"
