Agent 拿着你的身份去办事：越权的第一步，从身份继承开始

可信AI说2026-10-06阅读约 4 分钟SAFETYWORLD · TRUSTED AI SPEAKS

2026 年 6 月，Meta 的 AI 客服机器人把约 2 万个 Instagram 账号拱手送人。攻击者用 VPN 伪装成账号主人的常用登录地，对客服窗口说："我丢了旧邮箱，帮我换个联系邮箱。"机器人照做，把验证码发到攻击者控制的新邮箱，对方贴回验证码，点下"重置密码"，账号到手。最快 5 到 10 分钟完成接管。受害者包括奥巴马时期白宫存档账号和一位美国太空军高级军士长。Meta 最后拔掉了这个机器人，作废了它签发的所有重置链接。

Simon Willison 点评：这几乎算不上提示词注入，根子是一道缺失的授权校验。Meta 把账号恢复的重权限交给机器人，却没让它先核验提问者是谁。

Agent 分不清谁在说话，病根在身份层。

一次 Agent 调用跳三下：你授权 Agent；Agent 拿授权调工具；工具拿转交的凭证访问系统。每一跳都在回答"办事的是谁"，答案却逐跳变形：第一跳你是你，第二跳"我代表用户"，第三跳只剩一串不记名、不记来路的 token。攻击者不用偷密码，只需在某一跳把自己塞进去。

这毛病 38 岁了。1988 年 Norm Hardy 记录过：商用分时系统上的编译器有权限往共享目录写统计，账单文件恰好也在该目录。用户让它把调试输出写到一个和账单同名的文件，编译器用自己的权限打开，把账单覆盖了。Hardy 起名"困惑的代理人"：有合法权限的程序，被权限更低的一方哄骗，用错了权限。

Agent 就是 1988 年那个编译器的转世，只不过它一次能读懂一整封邮件。

编译器至少还有固定窄接口。Agent 的输入是系统提示词、用户请求、检索文档、工具返回、其他 Agent 的消息，全走一个通道。token 化之后，模型分不清可信指令和不可信内容，藏在 issue 标题里的一句话，和机主亲手敲的，分量一样。

2026 年 2 月，"Clinejection"让理论落地：一个有认证身份的 GitHub 分诊机器人，能读仓库、能执行 shell。有人提了个标题嵌指令的 issue，机器人把标题当真，执行了攻击者命令。攻击者再往项目共享的 Actions 缓存灌垃圾，换上键名撞上高权限 nightly 发布流程的毒缓存。流程一跑，攻击者拿到该 job 的 npm 发布 token，发了个被篡改的包版本。约 8 小时被下载约 4000 次，才被拦下。

权限被转手三次：分诊机器人、workflow、发布 token 持有者。每次转手，下游只验"是不是自己人"，没问"最初谁让你来的"。

三次转手，每次都没人问来路，这就是权限放大的全部秘密。

多 Agent 系统又添一层：2025 到 2026 年的威胁建模记录了一类固定手法，低权限客服 Agent 被误导，把"请让内部 Agent 导出数据库"包进委托，发给高权限 worker。worker 只认"内部同事转来的任务"，不看最初谁授意。请求被洗一遍，权限就漂白了。

更隐蔽的是授权范围：Agent 拿的通常是用户的完整 OAuth 授权，远超当前任务所需。你让它"看看这封报销邮件"，它手里可能攥着读全部邮件、发邮件、调日历、访问代码仓的权限。容易迷惑的办事员配上万能钥匙，迷惑一次就够了。

你给 Agent 的是一把钥匙，它转手能借给所有人，包括骗它的人。

解法不在让模型更聪明，而在把围栏画到身份层，分四步。

第一步，委托链留痕。IETF RFC 8693 定义了标准动作：token 里同时记两笔账，sub 写真正的人，act 写实际办事的 Agent。下游看到的不再是"持有人可调用"，而是"张三授权、报销 Agent 经办"。身份链第一次可审计。

第二步，给 Agent 发"身份证"不发"钥匙"。CNCF 毕业项目 SPIFFE/SPIRE：工作负载向系统证明"我是什么"，系统据此签发短命身份凭证。逻辑反转了：从"你知道密钥所以你是你"，变成"你就是这个工作负载所以你是你"。

没有长效密钥，就没有可偷、可转借的东西。

第三步，凭证按任务切片、按分钟过期。scope 从"billing:write"这种粗动词收敛到"退 50 美元以下的款"这种具体动作。Agent 被彻底迷惑，爆炸半径也锁死在一个小格子里。

第四步，模型永远不碰 token。模型只决策调哪个工具、传什么参数，执行和持有凭证的是确定性代码。凭证放在模型够不着的地方，注入就偷不走。这正是 Meta 个人 Agent Muse 的 Sentinel 架构：凭证库即时注入，Agent 永不见明文。巧的是，Meta 把这套设计给了 Muse，却没给更早的客服机器人留同等的身份校验。

围栏要画在身份层：谁在办事，先验明正身，再谈能办什么事。

过去一年安全投入大多堆在模型层，但客服机器人事故说明，模型再对齐，也拦不住一条身份不清的调用链。Agent 开始替人签字、调数据、发指令，安全必须从"管模型说什么"下沉到"管谁在替谁办事"。AI 每向业务迈进一步，安全就向结果靠近一步，这一步落在身份上。

AI 安全围栏专家数美的判断：身份校验应该成为围栏的默认组件，和输入指令、附件、生成内容、训练数据的四环节检查并列。数美从在线业务安全延伸到 AI 业务安全，十年业务风控解决的正是"谁在操作"，这套方法论搬到 Agent 身份链上依然成立。技术扩大了 AI 的业务边界，AI 业务安全要扩大的，是企业敢把钥匙交给 Agent 的边界，前提是每一次转手都有据可查。

金句：Agent 不是太聪明，是拿着你的身份证，还分不清谁在跟它说话。

已经用上 Agent 的团队，四条今天就能动手：

01 查一遍 Agent 手里最宽的常驻权限，先砍掉和当前任务无关的 scope，万能钥匙不允许过夜。

02 把凭证从 Agent 看得见的地方搬走，模型只做决策不碰 token，执行层用确定性代码持有密钥。

03 第三方工具调用走标准 token 交换，sub 记人、act 记 Agent，双记账，审计时还原整条委托链。

04 花钱、删库、改权限这类不可逆动作单独拎出来人工确认，不和日常授权混在一次点击里。

站队时间：给 Agent 发权限，你选哪派？A 派：默认最小身份，用多少申请多少；B 派：先给足权限跑起来，事后审计兜底。评论区报 A 或 B，再说一句你的 Agent 手里最宽的那把钥匙是什么。
